# readme-name-guardrail

Keeps a repository to **one** README. A file named `readme.md` — in any
capitalization (`README.md`, `ReadMe.md`, `readme.md`) — is only permitted at the
project root. Anywhere else it is denied, because dozens of identically-named
README files make it impossible to reference a single one from the terminal:
every file-picker, `@`-mention, and search collapses into a wall of same-named
hits. The fix the guardrail asks for is a descriptive prefix — `creatures-readme.md`,
`api-readme.md` — which reads fine in a listing and stays unambiguous.

The decision is a pure pattern match: filename equals `readme.md` (case-folded)
**and** the file is not the one directly in the project root. It spends no LLM
judgment.

**Claude Code only.** The payload is built on Claude Code's PreToolUse
permission-decision schema, so this plugin ships no Codex manifest and is absent
from the Codex catalog.

## What the plugin registers

Two PreToolUse hooks, sharing `hooks/readme-guard-common.ps1` (PowerShell):

1. **`^Write$` — `hooks/block-readme-write.ps1`.** The primary guard. When the
   agent tries to write a file whose name is `readme.md` (any casing) outside the
   project root, the Write is denied with a reason naming a prefixed alternative
   (drawn from the containing folder, e.g. a file under `creatures/` is suggested
   as `creatures-readme.md`). Creation is stopped at the source.

2. **`^Bash$` — `hooks/block-readme-git.ps1`.** The backstop. It parses `git add`
   and `git commit` commands and denies any that would stage or commit a
   forbidden README — covering files that arrived some other way (created by a
   shell command, generated by a tool, or committed before the plugin was
   installed). Non-git commands bail out immediately.

On install, Claude Code asks you to review and trust the hooks — that prompt is
the point of the guardrail being a plugin.

## What to expect after install

- Writing `docs/readme.md` is denied, with the reason suggesting `docs-readme.md`.
- Writing `README.md` at the project root passes.
- Writing `creatures-readme.md` anywhere passes — the prefix takes it out of scope.
- `git add docs/readme.md`, `git add .` (when a stray `readme.md` is untracked or
  modified under it), and `git commit`/`git commit -am "..."` with such a file
  staged are all denied, listing the offending path(s).

The deny is the guardrail working, not an error. Enable the plugin per project or
globally through the standard `/plugin` enablement scopes.

## Git command coverage

The Bash hook splits a compound command on shell control operators and inspects
each `git add` / `git commit` segment, honoring a `-C <dir>` repo override:

- **`git add <file>`** — the pathspec's basename is tested directly.
- **`git add .` / `-A` / `--all` / `-u` / `<dir>`** — the hook enumerates the
  affected files via `git status --porcelain` (scoped: `-u` excludes untracked; a
  directory pathspec is filtered to that subtree) and tests each.
- **`git commit`** — staged files (`git diff --cached --name-only`) are tested.
- **`git commit -a` / `-am`** — staged files plus tracked modifications
  (`git ls-files -m`) are tested.

## Adopting it in a project (optional escape hatch)

The guardrail is **active by default** wherever the plugin is enabled — no seam
required. The seam exists only to relax it. To disable or carve out exceptions in
a specific project, create `harness/readme-name-guardrail/config.json`:

```json
{
  "enabled": true,
  "allowPaths": ["^packages/[^/]+/readme\\.md$"]
}
```

- `enabled` (default `true`): set `false` to switch the guardrail off in this
  project without disabling the plugin globally — for a codebase that genuinely
  wants a README per package.
- `allowPaths` (optional): a list of regexes matched against the repo-relative
  POSIX path of a would-be README; any match is allowed through. Use it for a
  narrow, deliberate exception (a monorepo package layout, a docs generator's
  output) without opening the floodgates.

A missing, empty, or malformed config means "enforce with defaults." The config
is ordinary project configuration and should be committed; the guardrail writes
no runtime output, so no `.gitignore` entry is needed.

## Known limitations (accepted trade-offs)

- **"Project root" is the tool's working directory.** The single allowed README
  lives directly in the Write hook's `cwd` (and, for the git hook, the target
  repo's root). If you run the agent from a subdirectory, that subdirectory is
  treated as the root. This mirrors the convention used by the sibling guardrails.
- **Write is the only creation path guarded directly.** A `readme.md` created by
  a shell command (`echo > docs/readme.md`, `New-Item`, `cp`) is not blocked at
  creation time — it is caught later, when it is `git add`/`git commit`-ed.
- **Explicit `git commit <path>` pathspecs are not parsed.** Detecting them
  unambiguously alongside `-m "message"` is brittle; such a file must already be
  tracked, and the far more common staged/`-a` flows are covered. The Write hook
  and the `git add` coverage catch the file well before this point.
- **Leading-token git detection.** A git call hidden inside another command's
  quoted argument (`bash -c "git add ..."`) is not inspected, matching the
  deliberate simplicity of the sibling pattern-match guardrails.
- **Windows-first.** The hooks invoke `powershell`; the scripts are PowerShell
  5+/7 compatible but untested off Windows.
